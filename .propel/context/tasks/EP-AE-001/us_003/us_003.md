# US-AE-003: Rule Execution Orchestrator

## Story

As a batch audit runner, I need an orchestrator that systematically executes all deterministic rules against a patient cohort so that findings are complete, deterministic, and fully logged for reproducibility.

## User Value

A deterministic orchestrator ensures that every batch audit produces identical results when re-run on the same data and rule version. This reproducibility is critical for audit defense and compliance review.

## Acceptance Criteria

### Orchestration Pipeline
- [ ] Orchestrator loads:
  - Active rule pack (specified by version or defaults to latest)
  - Patient cohort (normalized FHIR resources from module_1_data)
  - Audit configuration (rule filters, execution parallelism, timeout settings)
  
### Execution Plan
- [ ] Before execution, orchestrator builds an execution plan:
  - List of rules to execute (in deterministic order: sorted by rule_id)
  - Dependency graph (if any rule depends on outputs of others)
  - Estimated runtime and resource budget
  - Plan is logged (traceable in audit output)
  
### Deterministic Execution
- [ ] Rules execute in deterministic order:
  - Order is fixed (sorted by rule_id) — never randomized or load-dependent
  - Same cohort + same rule pack → identical findings every time
  - Test: Execute batch A three times, verify output byte-for-byte identical
  
### Execution Logging
- [ ] Each rule execution is logged:
  - `execution_id` (UUID)
  - `rule_id` (from rule metadata)
  - `rule_version` (from rule pack)
  - `batch_run_id` (UUID, shared across all rules in a batch)
  - `cohort_size` (number of patient records)
  - `timestamp_start` (ISO 8601, rule execution start)
  - `findings_emitted` (count of findings produced)
  - `execution_duration_ms` (milliseconds)
  - `errors` (if any exception during execution)
  - `input_resource_snapshot_hash` (SHA256 of input cohort, for reproducibility verification)
  - `output_finding_hashes` (SHA256 of each finding, for verification)
  
### Error Handling & Resilience
- [ ] If a rule raises an exception:
  - Batch audit logs the error (rule_id, exception message, stack trace)
  - Execution continues with remaining rules (no hard stop)
  - Batch completion status notes that errors occurred
  - Operator is alerted (error queue or notification)
  
### Finding Emission
- [ ] Findings are emitted in deterministic order:
  - Sorted by rule_id (primary), then by resource_id (secondary)
  - No findings are cached or deduplicated (rules may produce overlapping findings)
  - Each finding retains reference to source rule and execution context
  
### No Rule Reuse or Caching
- [ ] Each batch audit:
  - Loads rule pack fresh (no cached rule objects from previous runs)
  - Executes each rule with fresh rule instance
  - Does not carry findings or state between batch runs
  
### Audit Trail Completeness
- [ ] Execution log includes:
  - Batch start and end timestamps
  - Rule pack version used
  - Cohort metadata (size, data source, normalization status)
  - All rule execution records
  - Summary: total findings, error count, average rule execution time
  
## Unit Tests
- [ ] Test suite covers:
  - Execution plan generation (correct rule order, estimate generation)
  - Rule execution in deterministic order (verified via logging)
  - Determinism test: same batch 3 times produces identical outputs
  - Error handling: rule exception → log error + continue, batch completes with error status
  - Logging: every execution logged with all required fields
  - No caching: fresh load on each batch audit
  - Finding order: sorted by rule_id then resource_id
  
## Integration Tests
- [ ] Full batch audit:
  - Load sample rule pack (5–10 rules)
  - Load test cohort (10–20 patients with sample contradictions)
  - Execute audit
  - Verify findings match expected contradictions
  - Re-run same audit, confirm identical findings
  - Verify audit log is complete and traceable

## Technical Notes

- Orchestrator pattern: builder (plan) → executor (run) → logger (audit trail)
- Sorting: Python sorted(rules, key=lambda r: r.rule_id) ensures determinism
- Logging: use structured logging (JSON) for auditability (e.g., python-json-logger)
- Reproducibility: hash inputs and outputs (SHA256) to detect any drift
- Consider thread-safe execution if parallelism is added later (but start with sequential)
