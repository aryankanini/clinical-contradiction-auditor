# US-AE-004: Safety Boundary Enforcement & Audit Logging

## Story

As a compliance enforcer, I need every rule execution to be logged and rule outputs to be immutable so that the audit-only boundary is provably maintained and findings cannot be tampered with.

## User Value

Safety boundary enforcement ensures that the product remains audit-only: rules detect contradictions, but never diagnose, prescribe, or alter clinical intent. Immutable logging provides evidence that this boundary has been maintained.

## Acceptance Criteria

### Audit Logging Foundation
- [ ] All rule executions (entry, completion, errors) are logged:
  - `execution_id` (UUID)
  - `timestamp_utc` (ISO 8601 with millisecond precision)
  - `rule_id` (rule being executed)
  - `batch_run_id` (batch context)
  - `rule_version` (version of rule pack)
  - `input_snapshot_hash` (SHA256 of normalized input resources)
  - `output_finding_count` (number of findings produced)
  - `execution_duration_ms`
  - `executor_identity` (user, service account, or batch process ID)
  - `status` (success, error, timeout, skipped)
  - `error_message` (if status = error)
  
### Immutability Enforcement
- [ ] Finding objects are immutable after rule emission:
  - Attempt to modify a Finding object raises AttributeError or TypeError
  - Use dataclass(frozen=True) or implement __setattr__ guards
  - Findings are sealed in audit log immediately after emission (no post-emission changes)
  
### Audit Log Persistence
- [ ] Audit log is append-only:
  - Only INSERT operations allowed (no UPDATE or DELETE on past entries)
  - Log is persisted to immutable storage (database with row-level locks, or file-based with read-only archive)
  - Log schema: immutable row IDs, no modification timestamps
  
### Safety Boundary Validation
- [ ] Every rule execution validates:
  - Rule does not modify input resources (deep-copy verification or read-only wrapper)
  - Rule output contains no diagnostic language (scan output for keywords: "diagnose", "prescribe", "treat", "alter", "clinical intent")
  - Rule does not emit treatment recommendations or clinical claims
  - Validator runs before finding emission (fail-safe: if rule violates boundary, finding is rejected and logged as error)
  
### Determinism Verification
- [ ] Before finding emission, orchestrator verifies:
  - Rule output is deterministic (no randomness, no timestamp variation)
  - Same rule + same input → same output (cryptographic check)
  - Findings are sorted in deterministic order (never randomized)
  - Test: execute rule twice on identical input, verify SHA256 match
  
### Audit Trail Searchability
- [ ] Audit log is queryable by:
  - `batch_run_id` (all executions in a batch)
  - `rule_id` (all executions of a rule)
  - `timestamp_utc` range (all executions in a time window)
  - `executor_identity` (all executions by a specific executor)
  - `status` (errors, timeouts, successes)
  
### Compliance Audit Interface
- [ ] Audit log provides:
  - Export function: `export_audit_trail(batch_run_id, format='json')` → full execution log
  - Verification function: `verify_finding_reproducibility(finding, log_entry)` → confirms finding matches log
  - Summary function: `audit_summary(batch_run_id)` → execution statistics, errors, safety checks passed
  
## Unit Tests
- [ ] Test suite covers:
  - Immutability: attempt to modify Finding raises AttributeError
  - Audit logging: every execution logged with all required fields
  - Append-only: cannot update/delete past log entries
  - Safety boundary validation: diagnostic keywords rejected, treatment recommendations blocked
  - Determinism check: identical input produces identical output
  - Audit trail query: correct entries returned by batch_id, rule_id, timestamp, executor
  - Export and verification: audit trail exports correctly, findings verified against log
  
## Integration Tests
- [ ] End-to-end audit logging:
  - Run batch audit with 5 rules
  - Verify all rule executions logged with complete metadata
  - Query audit log by batch_run_id, confirm all rules present
  - Export audit trail, verify JSON structure and completeness
  - Attempt to modify a Finding in log, confirm rejection

## Technical Notes

- Immutability: use `dataclass(frozen=True)` in Python; or implement custom `__setattr__` that raises
- Audit log: database with ACID guarantees (PostgreSQL, MySQL) or immutable file-based log (append-only text file with checksums)
- Safety scanning: regex or AST-based heuristic to detect diagnostic keywords in rule outputs
- Determinism check: use SHA256 hashing of rule output before and after to verify no variation
- Audit query: index audit log by batch_run_id, rule_id, timestamp for fast retrieval
