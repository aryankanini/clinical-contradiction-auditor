# US-AE-009: Stale State Detection Rules

## Story

As a data governance steward, I need to detect resources in terminal states that are outdated so that stale records don't masquerade as current information.

## User Value

Stale data erodes trust and creates reconciliation rework. A patient record with an inactive medication marked last_updated 200 days ago can mislead clinical staff into thinking recent data integrity checks have occurred. This story implements automated staleness detection.

## Acceptance Criteria

### Stale State Rule

#### Core Rule: Terminal State Outdated
- [ ] **Trigger:** Resource.status is terminal (resolved, completed, stopped, entered-in-error) AND Resource.lastUpdated ≤ (current_date - configurable_threshold)
  - Default thresholds: Condition/Medication 90 days, Procedure/Encounter 60 days, Observation 30 days
  - Thresholds are configurable per resource type
  
- [ ] **Applies to:** All resource types (Condition, Medication, Procedure, Encounter, Observation, CarePlan)

- [ ] **Finding:** Stale state — resource terminal but unreviewed for X days
  - Evidence: resource_id, resource_type, status, last_updated_date, staleness_days, configured_threshold, rule_threshold
  
- [ ] **Test cases:**
  - Resource at exact threshold: last_updated = 90 days ago, threshold = 90 → finding generated
  - Resource just below threshold: last_updated = 89 days ago, threshold = 90 → no finding
  - Resource well past threshold: last_updated = 200 days ago, threshold = 90 → finding with high staleness_days
  
### Exclusions
- [ ] Exclude resources with explicit archival intent:
  - If resource has `archive_date` or `archive_reason` field → skip stale check
  - If resource has `retained_for_compliance` flag = true → skip stale check (compliance holds)
  
### Staleness Scoring
- [ ] For each stale finding, calculate staleness intensity:
  - `staleness_days = current_date - last_updated_date`
  - `staleness_intensity = min(staleness_days / threshold, 2.0)` (capped at 2x threshold)
  - Higher intensity → higher finding severity (used in EP-AE-004)
  
### Performance & Scale
- [ ] Rule executes in <50ms per patient record (faster than cross-resource rules)
- [ ] Handle 1K–100K patient cohorts

### Evidence Payload
- [ ] Finding includes:
  - Resource ID, type, status
  - Last updated date
  - Staleness days and threshold
  - Reason staleness matters: "Stale terminal states may mask data quality issues"
  
### Test Scenarios
- [ ] Test data includes:
  - Resources at threshold boundary (90, 89, 91 days)
  - Well-past-threshold resources (6 months, 1 year old)
  - Archived/compliance-held resources (excluded)
  - Resources with null lastUpdated (handled gracefully: skip or flag as data quality issue)

## Technical Notes

- Rule config: YAML map of resource_type → threshold_days
- Last updated: use resource.meta.lastUpdated (FHIR standard field)
- Date comparison: normalize to UTC, current_date = today at 00:00 UTC
- Null handling: if lastUpdated is null, log as data quality issue, skip stale check
- Archival detection: check for archive_date or archive_reason fields
