# US-AE-010: Temporal Ordering & State Lifecycle Validation

## Story

As a timeline auditor, I need to detect impossible event sequences and invalid state transitions so that temporal data integrity is assured.

## User Value

Clinical data must follow logical event sequencing. Condition onset after treatment end, procedure dates inverted (end before start), or invalid status transitions signal data quality issues that compound in analytics and reporting.

## Acceptance Criteria

### Temporal Ordering Rule

#### Rule 1: Linked Resources Must Have Consistent Date Ordering
- [ ] **Trigger:** Linked resources have conflicting temporal order:
  - Condition.onset_date > Encounter.start_date (diagnosis after encounter started)
  - Procedure.performed_date < Encounter.start OR > Encounter.end
  - Observation.effective_date < Encounter.start OR > Encounter.end
  - Medication.start_date > CarePlan.end_date
  
- [ ] **Finding:** Temporal ordering contradiction — events out of sequence
- [ ] **Evidence:** Resource IDs, event dates, expected sequence, actual sequence
- [ ] **Test cases:** ≥3 cases (condition onset late, procedure before/after encounter, medication after plan ends)

#### Rule 2: Single-Resource Date Validity
- [ ] **Trigger:** Resource has inverted date range:
  - Encounter.end < Encounter.start (end before start)
  - Medication.start_date > Medication.end_date
  - CarePlan.period.end < CarePlan.period.start
  - Procedure.start_date > Procedure.end_date
  
- [ ] **Finding:** Date range impossible — end before start
- [ ] **Evidence:** Resource ID, start date, end date
- [ ] **Test cases:** ≥1 case per resource type

### State Lifecycle Validation Rule

#### Rule 3: Resource State Transitions Must Follow Valid Paths
- [ ] **State lifecycle per resource type:**
  - Condition: proposed → active → resolved | entered-in-error
  - Medication: active → on-hold | stopped | completed | entered-in-error
  - Procedure: preparation → in-progress → completed | stopped | not-done | entered-in-error
  - Encounter: planned → in-progress → finished | cancelled | entered-in-error
  - Observation: preliminary → final | amended | cancelled | entered-in-error
  - CarePlan: draft → active → completed | cancelled | entered-in-error
  
- [ ] **Invalid transitions rejected:**
  - Condition: resolved → active (can't resurrect resolved diagnosis)
  - Procedure: not-done → in-progress (can't move from terminal back to active)
  - Encounter: finished → in-progress (can't reopen closed encounter)
  
- [ ] **Finding:** State lifecycle violation — invalid transition detected
- [ ] **Evidence:** Resource ID, current status, previous status (if available from history), invalid transition rule
- [ ] **Test cases:** ≥2 cases per resource type

### Handling Null and Missing Dates
- [ ] Null/missing dates are handled gracefully:
  - If start_date is null, skip temporal checks (log as data quality issue)
  - If end_date is null, assume open-ended (still active)
  - If status is unknown, skip state lifecycle checks
  
### Timezone Awareness
- [ ] All timestamp comparisons are timezone-aware:
  - Normalize all timestamps to UTC before comparison
  - Handle UTC offset in FHIR resources (e.g., "2024-08-13T14:30:00-05:00" → UTC)
  - Test cases include DST boundary transitions
  
### Performance & Scale
- [ ] Rules execute in <100ms per patient record
- [ ] Handle 1K–100K patient cohorts

### Evidence Payload
- [ ] Finding includes:
  - Resource ID, type, status
  - Event dates (start, end, key milestones)
  - Expected vs. actual sequence/transition
  - Rule logic explanation
  
### Test Scenarios
- [ ] Test data includes:
  - Leap years (Feb 29 in leap year, handling non-leap years)
  - DST transitions (dates around spring forward, fall back)
  - Null/missing dates (handled gracefully)
  - Impossible transitions (clear violations)
  - Edge cases: future-dated resources, null status
