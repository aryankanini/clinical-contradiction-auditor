# US-AE-013: Audit Log Persistence & Reproducibility Validation

## Story

As a compliance officer, I need to verify that sampled findings can be reproduced from persisted audit logs so that findings are defensible in audit and legal review.

## User Value

Reproducibility is the foundation of audit defensibility. If we can re-run a finding from stored artifacts (rule, input snapshot, evidence, outcome) without re-processing the full pipeline, we prove the finding was generated correctly and hasn't been tampered with.

## Acceptance Criteria

### Audit Log Schema
- [ ] Audit log stores per-batch:
  - `batch_run_id` (UUID)
  - `rule_pack_version` (e.g., "2.1.0")
  - `cohort_size` (patient count)
  - `timestamp_start_utc` (batch start time)
  - `timestamp_end_utc` (batch end time)
  - `findings_emitted_count` (total findings)
  - `errors_occurred` (error count, if any)
  - `executor_identity` (user/service account)
  - Status: "success" or "partial" (if errors)

- [ ] Audit log stores per-finding:
  - `finding_id` (UUID)
  - `batch_run_id` (batch context)
  - `rule_id` (rule that generated finding)
  - `rule_version` (rule pack version)
  - `input_resource_snapshot_hash` (SHA256)
  - `output_finding_hash` (SHA256)
  - `evidence_payload` (full evidence object)
  - `timestamp_utc` (finding emission time)
  - `audit_outcome` (current status)
  - `executor_identity` (who processed finding)

### Input & Output Hashing
- [ ] Input snapshot hash:
  - Hash all input resources evaluated by rule (SHA256)
  - Hash deterministic (same resources → same hash)
  - Enable verification: "did the rule run on these exact resources?"
  
- [ ] Output finding hash:
  - Hash finding object (rule_id, resources, evidence)
  - Enable verification: "did the rule produce this exact finding?"

### Reproducibility Validation
- [ ] Given a `batch_run_id` and `rule_pack_version`, system can:
  1. Retrieve all findings for that batch from audit log
  2. For each finding, retrieve the rule from archived rule pack
  3. Reconstruct the rule inputs from input_resource_snapshot_hash
  4. Re-execute rule (or replay from log if available)
  5. Verify output finding matches persisted finding_hash
  
- [ ] Reproducibility status: "verified" or "mismatch" (findings differ)

### Persistence Layer
- [ ] Audit log is append-only:
  - Only INSERT allowed (no UPDATE, DELETE on past entries)
  - Use database with ACID guarantees (PostgreSQL, MySQL) or immutable file format
  
- [ ] Archive strategy:
  - Findings after N days (e.g., 30) moved to read-only archive
  - Archives are immutable, indexed, queryable
  - Retention: ≥7 years (HIPAA/compliance requirement, configurable)

### Audit Log Queryability
- [ ] Audit log is queryable by:
  - `batch_run_id` (all findings in batch)
  - `rule_id` (all findings produced by rule)
  - `severity_tier` (all CRITICAL findings, etc.)
  - `resource_id` (all findings involving resource)
  - `timestamp_utc` range (findings in date range)
  - `audit_outcome` (findings awaiting action, closed, etc.)

### Reproducibility Test & Validation
- [ ] Test protocol (≥95% reproducibility):
  1. Select 10 random findings from audit log
  2. For each finding, retrieve input snapshot hash and output finding hash
  3. Attempt to reconstruct/verify findings
  4. Confirm reconstructed findings match persisted findings
  5. Success rate ≥95% (1 failure allowed per 20 sampled)
  
- [ ] Test cases:
  - Recent findings (1 week old)
  - Older findings (6 months old)
  - Findings from different rule pack versions
  - Findings from different cohort sizes

### Compliance Audit Interface
- [ ] Audit log provides:
  - `export_audit_trail(batch_run_id, format='json')` → full execution log
  - `verify_finding_reproducibility(finding_id)` → verify finding can be reproduced
  - `audit_summary(batch_run_id)` → statistics, error count, reproducibility %
  
### Audit Trail Export
- [ ] Export format (JSON):
  - Includes all batch metadata, all findings with full evidence, all errors
  - Compatible with compliance tools (parseable, schema-validated)
  - Timestamps in ISO 8601 format
  
### Performance & Scalability
- [ ] Audit log performance:
  - Write: <10ms per finding
  - Query: <100ms for typical query (batch_run_id, rule_id)
  - Export: <1s per 100 findings

## Unit Tests
- [ ] Audit log persistence:
  - Finding written to log, retrieved correctly
  - Batch metadata persisted and queryable
  - Append-only enforcement (update/delete rejected)
  
- [ ] Hashing:
  - Input snapshot hash deterministic (same resources → same hash)
  - Output finding hash deterministic
  
- [ ] Reproducibility validation:
  - Finding reconstructed from log matches original
  - Input snapshot hash verified
  - Output finding hash verified

## Integration Tests
- [ ] Full batch audit → log persistence:
  - Run audit, generate 50+ findings
  - Persist all findings to audit log
  - Query audit log, retrieve findings
  - Verify all findings present and queryable
  
- [ ] Reproducibility test:
  - Select 10 random findings from log
  - Verify reproducibility for each
  - Confirm ≥9/10 reproducible (95%)

## Technical Notes

- Persistence: use PostgreSQL JSONB for audit log (immutable schema) or file-based log with checksums
- Hashing: use SHA256 for deterministic, collision-resistant hashing
- Archive: move findings to read-only schema/table after N days
- Retention: configure in environment (AUDIT_LOG_RETENTION_YEARS = 7)
- Query: index by batch_run_id, rule_id, resource_id, timestamp for fast retrieval
- Export: stream findings to JSON file (memory-efficient for large batches)
