# US-AE-012: Transparency Field Emission & Finding Hydration

## Story

As a compliance auditor, I need every finding to include mandatory transparency fields so that findings are reproducible and auditable.

## User Value

Transparency fields (rule ID, version, timestamp, audit outcome) enable reviewers and auditors to trace findings back to the exact rule and evidence that generated them. This traceability is essential for compliance and defensibility.

## Acceptance Criteria

### Mandatory Transparency Fields
Every finding MUST include all of the following:
- [ ] `rule_id` — identifier of the rule that generated this finding
- [ ] `rule_version` — version of the rule pack used
- [ ] `batch_run_id` — UUID of the batch audit that produced this finding
- [ ] `timestamp_utc` — ISO 8601 timestamp (millisecond precision) when finding was emitted
- [ ] `audit_outcome` — current audit status (value: "finding" at emission, later updated by operators to "accepted", "rejected", "escalated")
- [ ] `resources_evaluated` — list of resource IDs evaluated to produce this finding
- [ ] `evidence_payload` — complete evidence object (see US-AE-008)
- [ ] `severity_tier` — severity tier assigned (see US-AE-011)

### Finding Hydration Pipeline
- [ ] Hydration process:
  1. Rule execution → minimal output (contradicting resources, rule ID)
  2. Evidence extraction (US-AE-008) → enrich with field names, values, narrative
  3. Severity assignment (US-AE-011) → assign severity tier
  4. Timestamp stamping → add timestamp_utc and batch_run_id
  5. Validation → confirm all mandatory fields present
  6. Emission → write to persistence layer (US-AE-013)

- [ ] Hydration occurs immediately after rule execution (no buffering)

### Validation Before Emission
- [ ] Before emitting a finding:
  - Check all mandatory fields are populated (not null, not empty)
  - Validate field types (rule_id is string, timestamp_utc is ISO 8601, etc.)
  - Validate against Finding schema (US-AE-008)
  - If validation fails, log error, route finding to "remediation queue" (not emitted)
  
### Quality Gate: 90% Completeness
- [ ] ≥90% of findings have all mandatory transparency fields populated
- [ ] Findings with incomplete transparency are counted as "remediation queue" (non-actionable)
- [ ] Batch audit completion report includes transparency_completeness_pct metric

### Field Immutability Post-Emission
- [ ] After a finding is emitted:
  - Finding object is frozen (immutable)
  - Attempt to modify finding raises AttributeError or TypeError
  - Finding is sealed in audit log (no post-emission changes)

### Timestamp Resolution
- [ ] Timestamps have millisecond precision (ISO 8601 with 3 decimal places):
  - Example: "2024-08-13T14:30:45.123Z"
  - Millisecond precision sufficient for reproducibility and audit ordering

### Test Scenarios
- [ ] Generate 100 findings from diverse rules
- [ ] Verify all have all mandatory fields
- [ ] Verify ≥90% completeness (quality gate pass)
- [ ] Verify no findings have null mandatory fields
- [ ] Verify timestamps are ISO 8601 with millisecond precision
- [ ] Verify findings are immutable after emission (attempt to modify raises error)

## Technical Notes

- Hydration: implement as sequential pipeline (each step transforms finding)
- Immutability: use dataclass(frozen=True) or implement __setattr__ guard
- Timestamp: use datetime.datetime.utcnow().isoformat(timespec='milliseconds') + 'Z'
- Validation: use pydantic or custom validator on Finding model
- Quality gate: calculate transparency_completeness_pct = (hydrated_count / total_count) * 100
