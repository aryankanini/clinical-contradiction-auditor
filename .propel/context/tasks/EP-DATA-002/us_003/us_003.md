# User Story - US_003

## Story ID

- ID: US_003

## Story Title

- Define canonical normalized models

## Status

- **State**: Closed
- **Superseded By**: N/A
- **Change Request**: N/A

## Description

- As a platform engineer, I want canonical normalized models for statuses, timestamps, references, and provenance, so that all downstream contradiction checks operate on stable data contracts.

## Business Value

- Prevents each downstream module from inventing its own interpretation of FHIR fields and reduces contradiction-rule brittleness.

## Acceptance Criteria

### AC-01: Standardize normalization schema

- **Given**: The six in-scope FHIR resource families have source-specific field variations
- **When**: The shared normalized schema is defined
- **Then**: Each resource family maps into common status, timestamp, reference, and provenance fields
- **And**: The schema identifies which fields are required, optional, or derived

### AC-02: Preserve source traceability

- **Given**: A normalized record is produced from a source FHIR resource
- **When**: The normalized model is created
- **Then**: The model retains the source record identifier and field-mapping traceability
- **And**: The mapping is sufficient for later evidence reconstruction

### AC-03: Represent invalid or missing values explicitly

- **Given**: A source field is missing, partial, or invalid for normalization
- **When**: The normalized model is populated
- **Then**: The model records an explicit normalization outcome
- **And**: The pipeline does not silently coerce the field into a valid semantic state

## Edge Cases

- Multiple timestamps with different clinical meanings on the same resource
- Status fields that vary by resource family semantics
- References that resolve to external systems or unresolved local identifiers
