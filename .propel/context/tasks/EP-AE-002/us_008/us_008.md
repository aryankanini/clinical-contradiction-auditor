# US-AE-008: Evidence Extraction & Finding Emission

## Story

As a finding reviewer, I need each contradiction finding to include direct links to the contradicted resources and the exact fields that conflict so that I can investigate without secondary queries.

## User Value

Complete evidence in findings enables reviewers to quickly understand the contradiction without reconstructing data queries. This accelerates triage, reduces query overhead, and ensures findings are defensible in audit review.

## Acceptance Criteria

### Finding Schema
- [ ] Finding object contains all mandatory fields:
  - `finding_id` (UUID)
  - `rule_id` (rule that generated this finding)
  - `rule_version` (version of rule pack)
  - `batch_run_id` (batch context)
  - `timestamp_utc` (finding emission time, ISO 8601)
  - `audit_outcome` (generated as "finding" at emission)
  - `resource_ids` (list of resource IDs involved in contradiction)
  - `resource_types` (list of resource types, e.g., ["Condition", "CarePlan"])
  - `contradiction_type` (rule name or category, e.g., "active_condition_closed_plan")
  - `severity_tier` (placeholder, assigned in EP-AE-004, values: CRITICAL, HIGH, MEDIUM, LOW)
  - `evidence_summary` (human-readable contradiction description)
  - `conflicting_fields` (list of field names that contradict)
  - `field_values` (dict mapping field names to actual values, e.g., {"condition.status": "active", "careplan.status": "completed"})
  
### Evidence Summary Format
- [ ] `evidence_summary` is human-readable and narrative:
  - Example: "Condition (cond-123) status='active' but related CarePlan (cp-456) status='completed' with end_date='2024-08-01'. Active diagnosis requires active care plan."
  - Includes: resource IDs, contradicting status/date values, rule logic in plain language
  - Length: 100–300 characters (enough for context without verbosity)
  
### Resource References
- [ ] Finding includes FHIR-style resource references (not full resources):
  - Format: `{resource_type}/{resource_id}`
  - Example: "Condition/cond-123", "CarePlan/cp-456"
  - References are in `resource_ids` and `field_values`
  
### Field Indexing
- [ ] `conflicting_fields` is indexed for grouping findings by field type:
  - Example: ["status", "end_date"]
  - Enables queries like "find all findings with status contradictions"
  
### Finding JSON Schema
- [ ] Finding validates against canonical Finding schema (SchemaVer 1.0):
  - Schema defines: required fields, field types, constraints
  - Stored in `module_2_audit_engine/schemas/finding_schema.json`
  - Validation on emission (fail-safe: malformed findings rejected)
  
### Quality Gate: Evidence Completeness
- [ ] ≥95% of emitted findings populate all mandatory evidence fields
- [ ] Findings with incomplete evidence are logged as data quality issues
- [ ] Batch audit completion report includes evidence completeness % (metric for monitoring)

### Evidence Extraction Logic
- [ ] Evidence extractor runs after rule execution:
  1. Rule produces raw findings (minimal: contradicting resources, rule ID)
  2. Extractor enriches findings: resolves resource details, extracts conflicting fields, builds narrative
  3. Extractor handles missing data gracefully (missing fields logged, not fatal)
  4. Extractor outputs fully-hydrated Finding objects
  
### Test Coverage
- [ ] Test dataset includes:
  - ≥20 sample contradictions from different rule types (Conditions, Medications, Encounters, etc.)
  - Verify all findings parse valid JSON and conform to schema
  - Verify evidence_summary is human-readable and complete
  - Verify field_values are accurate (no hallucinated values)
  
## Unit Tests

- [ ] JSON validation: Finding serializes/deserializes correctly
- [ ] Evidence quality: summary is complete and narrative makes sense
